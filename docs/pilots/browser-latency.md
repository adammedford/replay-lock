# Browser development latency pilot

The paired [raw report](browser-latency.json) measures the pinned Epic Stack checkout (`8473afd804b66dba6a23f317908dc35d1535e90d`) on an Apple M4 Pro with Node 22.19.0. The prepared checkout includes the documented middleware-host integration from the earlier Epic pilot; its `server/index.ts` SHA-256 is `f23699ed680106b0dd5fbefd41490cbd21479fb25ebd0c4b38a46d6f993eb29f`, and the preserved original Vite config SHA-256 is `678efe0d588b484560001dc97c0024454d12420462f1fd849b7e35da8d8b70cf`. Five alternating enabled/disabled pairs used a fresh application process and browser for each run, removed Vite's dependency cache before launch, and exercised the existing users search route. Page load ended when the body appeared, navigation when its heading appeared, and HMR when an edit to that heading became visible. The edit and Vite config were restored after each trial. The runner's SHA-256, source and lockfile SHA-256, raw samples, and process-group cleanup results are in the report. The ReplayLock build used by the linked Epic plugin had `dist/vite-plugin.js` SHA-256 `5ff0cf2fdcbce6505439cb7d7fe624274d8a5e6fc517d4b2a7e6cead11046d3d` and `dist/dev-server.js` SHA-256 `485e39f29367f9338a91623340f7f181b9d0c9ed1f71dd28be27a73a2267a817`.

| Browser-visible milestone | Disabled median | Enabled median | Added median | Ratio |
| --- | ---: | ---: | ---: | ---: |
| Cold page | 3,957 ms | 6,994 ms | 3,037 ms | 1.77x |
| Search navigation | 201 ms | 299 ms | 99 ms | 1.49x |
| Visible HMR | 880 ms | 16,113 ms | 15,233 ms | 18.31x |

All ten trials completed and each owned application process group exited. No timeout was entered as a successful latency. This benchmark records development responsiveness; the earlier synthetic transform benchmark did not measure browser-visible latency.

The [proposed budget](browser-latency-budget.json) caps the *added median* at 2 seconds for cold page and visible HMR, and 100 ms for navigation. The HMR budget reflects an interactive edit loop: a 16-second wait is too slow to treat as acceptable even if characterization succeeds. The smaller navigation allowance keeps routine page changes responsive. This is a proposal, not a previously agreed target. The present build exceeds the cold-page and HMR ceilings; navigation's 99 ms added median falls just below its 100 ms ceiling, with little margin. Run the explicit comparison with `node scripts/check-browser-budget.mjs docs/pilots/browser-latency.json docs/pilots/browser-latency-budget.json`; it should fail until overhead improves. `node scripts/bench-dev-browser.mjs --check docs/pilots/browser-latency.json` verifies the evidence without enforcing proposed ceilings. The thresholds are deliberately outside ordinary correctness CI.

The visible HMR overhead dominates the current measurements. A separate one-pair V8 CPU profile reproduced a 16,475 ms enabled HMR versus 894 ms disabled HMR. In the enabled application process, 6,709 of 31,598 self samples were in ReplayLock's `effect-analyzer.js`, 894 in `dev-analysis.js`, 8,218 in TypeScript, and 3,143 in filesystem work. The disabled application process had 5,711 samples total, with none in those ReplayLock analysis modules. The profile covers startup, navigation, and HMR together, so it supports repeated project analysis as the leading investigation target without attributing an exact number of HMR milliseconds to one function. Temporary profiling used a one-pair copy of the runner and V8 `--cpu-prof`; that copy was removed. The unprofiled ten-run report above remains the budget evidence.
