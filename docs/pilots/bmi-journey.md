# Unattended BMI application characterization pilot

The isolated application was [SmartVK BMI Calculator at `5b32cf94ed51ab00c43a2d98ffb410270bbeebd4`](https://github.com/Vkrmoo7/smartvk-bmi-calculator/tree/5b32cf94ed51ab00c43a2d98ffb410270bbeebd4). Its existing form invokes `getBMICategory` and `getHealthSuggestions` as a user edits height and weight. The source `package.json` and lockfile hashes in the [recording report](bmi-owned-record.json) match the pinned archive throughout the pilot. The app received only a Vite plugin import and `replaylock({ dev: true })` in `vite.config.ts`; its business logic and dependency declarations stayed intact.

ReplayLock was built and packed as `replaylock-0.1.0.tgz` (SHA-256 in the report). The app's dependencies were restored with `npm ci --ignore-scripts`; the packed library was installed into a separate npm consumer and linked at `node_modules/replaylock` to prevent its Vite 8/Vitest dependencies from being hoisted into the application's Vite 5 tree. A direct `npm install --no-save` in the app allowed recording but caused browser replay to load the wrong `expect-type` export. The isolated consumer layout resolved that conflict without changing the app lockfile.

The unattended [recording runner](../../scripts/pilot-bmi-owned-record.mjs) launched `replaylock record -- npm run dev`, drove the [existing form](../../scripts/pilot-bmi-browser.mjs) using synthetic height 170 cm and weight 70 kg, and stopped via ReplayLock's authenticated local control endpoint. The browser asserted the visible `Normal weight` category and suggestions. It aborted all nonlocal requests; four attempted Gemini requests were blocked. The source archive's `.env` was omitted from the disposable checkout. The app itself raised two `age`-of-undefined page errors during its initial AI effect; the BMI panel still worked. No app logic was changed to hide these errors.

The run recorded 21 completed observations and retained **two pending candidates**, protecting `getBMICategory(24.2) → "Normal weight"` and the four plain suggestion records for `(24.2, "Normal weight")`. The session was **partial**: 13 `UNSUPPORTED_VALUE` blocks occurred on these helpers during early invalid form states, plus one `INCOMPLETE_OBSERVATION`. The controller exited with status 2 to report that partial capture. Thus this is a demonstrated useful characterization journey for two valid inputs, not a claim of clean recording for every app invocation. The report's `status: passed` refers to the scoped workflow and unattended cleanup: the controller and output pipes closed, the listener and discovery metadata disappeared, and the probe sent no termination signal.

Both synthetic candidates were [reviewed and accepted interactively](bmi-review.json) after inspecting their complete inputs, traces, completions, and partial-capture provenance. The [validation report](bmi-validation.json) contains the accepted arguments, empty external traces, and return completions. Offline replay verified both cases with native outbound network operations blocked. A comment-only edit passed the same two cases. Moving the app's `getBMICategory` threshold from 24.9 to 24.0 made the recorded 24.2 input return `Overweight`; verification failed with `OUTPUT_MISMATCH`, naming that case and expected/actual values. The edit was restored, and the source hash matches its original value. These pure helpers do **not** demonstrate nonempty effect-trace correlation in this application; controlled effect tests cover that contract separately.

Reproduction from a fresh isolated checkout requires Node 22, the pinned app archive without `.env`, `npm ci`, an isolated consumer installation of the built tarball, a link from the app's `node_modules/replaylock` to that consumer's package, and the two-line Vite plugin wiring. Run the owned recording script with the app root, a report path, a free loopback port, and the tarball path. From a fresh `.replaylock` data directory, run `node node_modules/replaylock/dist/cli.js review`, inspect each synthetic input, trace, completion, and provenance, and make each acceptance decision interactively; then run `scripts/pilot-bmi-validate.mjs` with the app root and a report path. The latter runs the three offline replay controls and restores the validation edit in `finally`. Keep the source and tarball identities fixed when repeating the final pilot.
